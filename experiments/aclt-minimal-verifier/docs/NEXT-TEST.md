# 下一项测试：调度器中断后恢复

状态：**已实现并执行，12/12 场景通过**。本文保留当时的验收方案；实际实现与注入方式见 [恢复测试报告](RECOVERY-REPORT.md)。

## 要回答的问题

Rust 调度器突然被强制终止后，再次启动，能否继续同一个任务，并且不漏块、不重复计入、不恢复已经用完的重试额度、不把旧进程的结果当成新结果？

继续使用单台 Ubuntu 电脑、现有整数输入、两个计算进程上限。首轮只强制终止调度器进程；操作系统保持运行，不将通过结果解释成断电安全。

## 在测试之前需要补上的能力

方案制定时，程序拒绝已有运行目录，进度主要在内存里。以下是本轮已补齐的能力：

1. **保存运行进度**：输入快照、固定参数、每块已消耗的尝试次数、当前尝试和已通过结果。每次记录何时生效必须有明确顺序。
2. **新增显式恢复入口**：原来的新建命令继续拒绝旧目录；恢复命令只处理可识别且检查通过的运行记录。
3. **一次只能有一个调度器**：用操作系统级锁防止同时恢复同一个任务；进程退出后锁应自动释放，不能只靠一个可能遗留的文件判断。
4. **隔开重启前后的尝试**：恢复后先使旧的未完成尝试失效；新进程使用新的尝试编号与输出位置。不要让旧进程和新进程共写结果文件。
5. **处理遗留进程**：启动前确定旧工作已退出或已可靠回收，才重新占用名额。不能仅凭日志里的 PID 就终止进程，PID 可能已被复用。需选择并验证进程组或受监督的子进程生命周期方案。
6. **设置明确的测试暂停点**：测试驱动等到指定步骤的确认信号，再发送 SIGKILL。不要只靠固定等待几毫秒猜测中断位置。

建议采用保守的次数规则：先保存“本次尝试额度已占用”，再启动计算进程。如果恰在这两步之间中断，该次额度仍算消耗；允许少做一次，不能靠反复重启无限增加执行次数。

## 首轮验收场景

| 编号 | 在哪里中断或制造问题 | 通过条件 |
|---|---|---|
| R01 | 输入和参数保存后，尚未启动工作 | 恢复后可以完成，输入和参数不变 |
| R02 | 尝试额度保存后，进程尚未启动 | 不返还已消耗额度，后续次数不超限 |
| R03 | 两个计算进程执行期间 | 旧进程被处理后再恢复派发，同时存活的计算进程不超过两个 |
| R04 | 结果已写出，但通过状态尚未保存 | 对结果重新检查或重派，不因文件存在就认定通过 |
| R05 | 某块的通过状态已保存 | 恢复时核对保存结果，该块不重复计入；完整记录不应无故重算 |
| R06 | 已记录超时，但尚未启动重派 | 旧尝试持续无效，重派额度不被重置 |
| R07 | 最终临时文件已写，尚未改名 | 不把临时文件当最终结果，恢复后完整检查再发布 |
| R08 | 最终结果已改名，完成记录尚未保存 | 核对已有最终结果并补齐状态，不重复启动工作或覆盖有效结果 |
| R09 | 重复恢复，或两个恢复命令同时启动 | 已完成任务返回一致结果；同时最多一个调度器取得运行权 |
| R10 | 多次中断，直到尝试额度耗尽 | 持久记录中的次数累积不丢失，明确失败且不发布最终结果 |
| R11 | 进度记录截断、内部损坏或输入不匹配 | 不猜测完成状态；拒绝恢复且不启动计算，保存证据供排查 |
| R12 | 重启前的旧结果迟到 | 即使统计正确也不计入新尝试，不改变最终结果 |

首轮对于无法确认完整性的运行记录，选择明确拒绝恢复。自动修复部分记录可留到后续，避免第一版把“猜测修复”当成“成功恢复”。

## 统一通过条件

- 最终统计与原始输入的独立重算一致；故障任务不发布最终成功结果。
- 每块只计入一次，尝试总数在重启前后累计，永不突破设定上限。
- 旧结果不能变成新结果；并发恢复不能同时派发。
- 测试可观察进程生命周期，不能只查看新调度器内存中的进程数量。
- 恢复记录损坏时明确报错，不静默从头启动并重置额度。
- 现有 68 个基础案例和 12 个多进程场景仍全部通过。
