# ACLt 审计程序

> 状态：`ACCEPTED`  
> 生效日期：2026-08-18  
> 最后复审：2026-08-18  
> 适用范围：语义连续性、文档变更、Gate 退出、实现一致性、发布准备和历史档案审计  
> 配套模板：[`audit-report-template.md`](audit-report-template.md)

## 1. 目的

本程序规定 ACLt Protocol 审计必须使用的共同基线、证据规则、执行阶段、结论格式和交付条件。目标是使不同时间、不同审计者和不同实现产生可复核、可比较且不会夸大成熟度的结果。

任何审计都必须同时回答：

1. 审查的准确对象、提交和时间是什么？
2. 哪些内容是事实、决定、候选方向、假设或未决问题？
3. 变更是否在全部权威文档中保持语义连续？
4. 威胁、不变量、协议函数、状态机、证明义务和测试是否可追踪？
5. 历史材料是否被误当作当前规范？
6. 当前证据允许通过什么，不允许宣称什么？
7. 需要更新哪些文件，复制到哪些仓库目录？
8. 交付文件是否经过结构和完整性复核？

## 2. 审计类别

所有类别使用本程序的共同流程，只允许调整核查深度，不得跳过基线、证据、结论和交付规则。

| 类别 | 触发条件 | 必须重点检查 |
|---|---|---|
| 语义连续性审计 | 新决定、术语、架构或安全边界变化 | 前后语义、ADR、威胁、不变量、协议、状态和未决问题 |
| 文档变更审计 | 文档新增、改写、移动或删除 | 权威位置、链接、编号、时间戳、重复权威和历史边界 |
| Gate 退出审计 | 声称 G0–G6 任一 Gate 可以退出 | 退出条件、证据清单、反例、阻断项和禁止主张 |
| 实现一致性审计 | schema、validator、runtime、frontend 或适配器变化 | 规范—实现—测试映射、差分结果、失败关闭和迁移 |
| 发布准备审计 | 对外发布、版本升级或试点 | 许可、名称、成熟度、供应链、安全响应和回滚 |
| 历史档案审计 | 导入、引用或重新解释旧材料 | 原文保留、时间戳、`SUPERSEDED` 标记和当前权威入口 |

## 3. 不可省略的审计约束

1. **固定基线。** 审计开始前记录仓库、分支或标签、完整 commit SHA、快照时间和时区。
2. **读写分离。** 审计本身默认只读；发现问题后可以准备本地修订文件，但提交、推送、分支和 Pull Request 必须由获得授权的独立流程完成。
3. **不以实现反向定义规范。** 可运行代码只能提供证据，不能覆盖规范对象、不变量或已接受 ADR。
4. **不静默修复历史。** 历史正文与原时间戳保留；冲突通过索引、警告和 `SUPERSEDED` 状态显式隔离。
5. **不夸大结论。** 局部一致、测试通过或语义连续性通过，不等于 Gate 退出、安全证明、生产就绪或整体鲁棒。
6. **保留失败证据。** 反例、失败测试、未知项和阻断项必须进入报告，不得只交付修订后的“干净结果”。
7. **结论可复现。** 报告必须提供足够的文件、编号、命令类别、输入和哈希，使另一审计者能够复核。

如需偏离本程序，必须在审计报告的“偏离记录”中说明原因、风险、补偿措施和批准者；未记录的偏离使审计结论无效。

## 4. 证据与权威顺序

发生冲突时按以下顺序裁决：

1. 较新的明确项目决定；
2. 当前 ProtocolVersion 的规范对象、状态机和不变量；
3. 已接受 ADR；
4. 当前权威文档；
5. 历史项目文件；
6. 未接受草案或助手建议；
7. 外部文献。

补充规则：

- 仓库外的明确决定可以作为变更依据，但必须在报告中标明来源日期，并在同一变更集中落入 ADR 或相应权威文档。
- 外部资料只能支持理论边界、工程先例或候选方法，不能替 ACLt Protocol 证明组合系统。
- 搜索摘要、文件名、提交信息和二手转述不能替代完整文件内容。
- 事实、推断和建议必须在报告中分开表达。

## 5. 标准审计流程

### A0 — 授权与边界冻结

记录：

- 审计目标和类别；
- 允许的只读操作；
- 是否允许准备本地修订；
- 明确禁止的仓库写操作；
- 审计基线和排除范围。

输出：审计任务头。如果基线或权限无法确定，结论为 `BLOCKED`，不得继续作确定性判断。

### A1 — 仓库与文档盘点

建立准确清单：

- 当前文档、历史文档、规范、实现、测试和许可证；
- 每个文件的仓库相对路径；
- 新增、修改、删除和未变化文件；
- 当前权威入口及目录职责；
- 基线 commit SHA 和最新相关提交。

不得用计划目录替代实际目录，也不得把历史档案计入当前规范文档数量。

输出：文件清单与目录映射。

### A2 — 时间戳与来源核查

逐项核对：

- 文件中的决定日期、更新日期、最后复审日期；
- Git 提交时间与时区；
- 外部决定或证据的发生日期；
- 历史文件的原时间戳；
- 报告和警告标记的审计日期。

规则：

- 使用 ISO 8601 日期；精确事件记录时写明时区。
- 决定日期不得因复审而改写。
- 只有实际完成内容复审的文件才能更新“最后复审”。
- 历史正文的原日期不得覆盖；新增警告单独记录复审日期。
- 时间无法确定时写 `UNKNOWN` 和原因，不得猜测。

输出：时间戳差异表。

### A3 — 语义差异提取

对每个变更记录：

- Change；
- 触发问题、反例或决定；
- 变化前状态与变化后状态；
- 受影响的对象、函数和角色；
- 受影响的 DP、TH、INV、ADR、CLM、OQ、PO 和 Gate；
- 新增假设、兼容性、迁移和残余风险；
- 需要同步的权威文件。

输出：语义差异矩阵。纯排版变化与语义变化必须分开。

### A4 — 跨文档连续性核查

至少检查以下同步链：

```text
Decision / evidence
  ├── overview and terminology
  ├── ADR
  ├── threat model
  ├── invariants
  ├── architecture and protocol
  ├── analysis and claims
  └── current status and open questions
```

强制检查：

- 同一术语是否只有一个当前含义；
- 同一结论是否形成多个互相独立的权威版本；
- 状态标签是否一致；
- Gate 定义是否一致；
- 禁止主张是否同步；
- 已决定事项是否仍被列为完全开放；
- 尚未证明的内容是否被写成已完成。

输出：连续性核查表和冲突清单。

### A5 — 安全与可实现性追踪

建立或核对：

```text
Threat → Invariant → Protocol function/state transition
       → Proof obligation → Test/conformance evidence
```

每个状态转换必须说明所保持的不变量。并发、重试、崩溃、分区、恢复、迁移和适配器替换不得绕过不变量。无法证明合法性时，必须拒绝、回滚或进入已定义的安全终态。

审计必须先给发现分配证据层，避免把所有问题都误判成“需要数学证明”：

| 层 | 审计问题 | 合格证据 |
|---|---|---|
| 结构 | 输入是否唯一可编码、可解析 | Schema、canonical vectors |
| 算法 | 相同完整输入是否唯一输出 | 纯函数、定理、模型检查、差分对拍 |
| 来源忠实性 | 输入是否由真实状态机产生且无已知旁路 | 接口/权限审计、日志、故障注入、恢复和集成测试 |
| 部署风险接受 | 哪个网络在何组件和损失边界内启用能力 | 版本化 assurance、有效期、组件清单、风险预算、撤销演练 |

结构或算法不可两解是接口实现的阻断项。来源或部署证据尚未建立时，可以继续实现接口，但相应能力必须保持 `DISABLED/AUDIT_ONLY` 或 fail closed。不得以“没有开放世界形式证明”为由阻塞与该假设解耦的 Schema、validator 和测试，也不得以“已经实现”为由把来源事实升级成数学真理。

对于 V1，至少检查：

- 规范对象字段、版本、canonical encoding 和哈希域；
- RIR schema、canonical representation 和 validator；
- Rust Profile lowering 与未来 frontend conformance；
- runtime effects、资源、终止、错误和 checkpoint 语义；
- 验证器注册、结果等价和统计适用条件；
- 资金锁定、耗尽、退款、故障归因和 at-most-once 结算；
- reference implementation、golden vectors、差分测试和故障注入。
- MainnetAssuranceProfile、CauseSet/reducer、ExecutionCapability 与 append-only/finality 日志 contract；
- Type A 文件向量与 Type B 数据流/权限/恢复审计是否分开。

输出：追踪覆盖率、孤立项和阻断证据。

### A6 — 历史档案与权威性审计

检查：

- 历史目录是否有明确索引；
- 旧文档是否会被误解为当前规范；
- 旧角色、Rank、51%、发行、Foundation 或中心控制语义是否重新渗入；
- 冲突文件是否标记 `SUPERSEDED`；
- 警告是否链接到当前权威入口；
- 原正文和原时间戳是否保持。

输出：历史冲突清单和处理决定。除非另有明确授权，不删除历史证据。

### A7 — 许可证、发布与外部事实核查

检查：

- 根目录许可证实际内容与文档陈述是否一致；
- SPDX、NOTICE、第三方许可和贡献机制状态；
- 代码许可与规范、文档、论文、名称和商标边界；
- 所有可能变化的外部事实是否使用当前一手来源核实；
- 名称、版本和成熟度声明是否会误导用户。

输出：外部事实来源表及发布阻断项。

### A8 — 结构与机械一致性检查

至少执行：

- 每份 Markdown 恰有一个 H1；
- fenced code blocks 成对；
- 相对链接目标存在；
- 文件路径与文档索引一致；
- 追踪编号唯一、无缺号重用；
- DP、TH、INV、ADR、CLM、OQ、PO 和 Gate 计数符合当前登记；
- 不存在已知过期短语；
- 更新包不含缓存、渲染图、临时文件、凭据或工作环境元数据。

输出：检查命令类别、结果和异常。机械检查通过不等于语义审计通过。

### A9 — 结论判定

审计必须分别判定，禁止合并成模糊的“通过”：

| 维度 | 允许值 |
|---|---|
| 语义连续性 | `PASS` / `FAIL` / `BLOCKED` |
| 目标 Gate | `PASS` / `FAIL` / `NOT_ASSESSED` |
| 结构完整性 | `PASS` / `FAIL` |
| 历史隔离 | `PASS` / `FAIL` / `NOT_APPLICABLE` |
| 发布准备 | `PASS` / `FAIL` / `NOT_ASSESSED` |

标准结论必须使用以下格式：

> 语义连续性：{结果}；{Gate} 退出：{结果}；结构完整性：{结果}。  
> 允许开展：{被证据支持的下一步}。  
> 禁止宣称：{尚未被证据支持的成熟度或安全主张}。

发现项分级：

- `BLOCKER`：使审计目标或 Gate 无法通过；尚未证明某候选“全局最优”本身不是 BLOCKER，除非目标明确承诺该最优性或缺失会使算法不可调用/能力无法 fail closed；
- `MAJOR`：会造成语义、安全、许可或实现不一致；
- `MINOR`：不改变核心语义，但需要修正；
- `NOTE`：观察项或后续建议。

每项使用稳定编号 `AUD-YYYYMMDD-NNN`，并记录证据位置、影响、修复要求和状态。

### A10 — 修订、回验与交付

如审计范围允许准备修订：

1. 只修改已识别的目标文件；
2. 保持仓库相对路径；
3. 同步所有受影响的权威文档；
4. 再次执行 A2–A9；
5. 生成只含变更文件的更新包；
6. 生成独立审计报告和目录映射；
7. 计算更新包哈希并验证压缩完整性；
8. 明确列出未变化、故意排除和仍待处理的文件；
9. 将提交、推送和 Pull Request 留给授权流程。

只有回验通过，才可把本轮发现标记为 `RESOLVED_IN_PREPARED_CHANGE`；在变更合入目标分支前，不得标记为 `CLOSED_ON_MAIN`。

## 6. 审计完成条件

一次审计只有同时满足以下条件才算完成：

- 基线、范围、时间和权限明确；
- 所有证据可定位；
- 事实、推断、建议和未决项已分离；
- 连续性与 Gate 结论分别给出；
- 全部 `BLOCKER` 和 `MAJOR` 已处理或明确保留；
- 时间戳和历史证据未被篡改；
- 结构与链接检查完成；
- 修订后执行过完整回验；
- 报告、目录映射、文件数量和哈希齐全；
- 未执行未经授权的仓库写操作。

## 7. 本程序的变更

本程序本身属于治理规范。修改它必须：

1. 说明现有程序无法处理的具体问题；
2. 保留旧版本和变更日期；
3. 更新配套报告模板；
4. 对至少一次既有审计进行回放验证；
5. 在审计报告中记录偏差和迁移影响。

任何较简化的检查单只能作为本程序的执行视图，不能删除上述强制阶段或降低证据要求。
