# 多分支并行开发流程

> 文档状态：Living engineering policy（2026-11-14 维护者批准采用）\
> 流程版本：PARALLEL-1\
> 最后更新：2026-11-14\
> 适用范围：本仓库多个主题分支同时开发，以及 Claude Code 会话的规划、实现、审计与合入

## 1. 范围与权威边界

本文细化 [ENV-1 §6](environment-standard.md#6-git-与文件协作约定) 的主题分支约定。它规定多个分支同时开发时的会话分工、授权、冲突处理与审计。

本文是协作流程，不定义协议语义，不改变 SemanticStatus、VersionDisposition、ADR、Gate 或统计参数。以下文件继续适用：

- [贡献指南](../../CONTRIBUTING.md)
- ENV-1 其余条款
- [DUALHOST-SSH-1](dualhost-ssh-validation.md)
- [审计程序](audit-procedure.md)

本文与它们冲突时，以它们为准，并修订本文。第 7 节的 PR 审计不替代审计程序 A0–A10 的完整审计；阶段收尾和发布仍按审计程序执行，并把报告入库。

本文合入 `main` 后生效。生效前，提交、推送和 PR 仍按 ENV-1 §6 逐次取得授权。

## 2. 采用时的仓库事实（2026-11-14 核对）

下列事实决定了本流程的形状。它们变化时，应修订相应规则。

- **合并方式与分支保护：** GitHub 仓库只允许 squash 合并，合并后自动删除源分支。远端只有 `main`，没有标签。私有仓库在当前方案下不能启用分支保护，也未开启 “Update branch”。因此 PR 的 CI 只针对推送时的 `main`，合并前与最新 `main` 同步只能靠本流程保证。
- **热点文件：** `main` 最近 25 次合入中，修改次数如下：
  - `SINGLEHOST-SHA256SUMS`：25 次
  - `docs/07-roadmap/current-status.md`：22 次
  - `docs/README.md`：13 次
  - `Makefile`：12 次

  并行分支在这些文件上会反复冲突。
- **证据提交的可达性：** `scripts/check-repository-evidence.py` 按证据摘要中的 `source_revision` 从 Git 读取文件。被钉住的提交如果只存在于已删除的特性分支上，完整克隆中就取不到它。
- **共享实验资源：** 最简验证机的多虚拟机实验使用固定端口（`multivm.py` 的 `JOB_PORT = 7400`），物理双机只有一台 B 机。两项实验不能在同一宿主或同一台 B 机上同时运行。

## 3. 角色

| 角色 | 数量与位置 | 职责 | 不做 |
|---|---|---|---|
| 维护者 | — | 批准计划卡；在 GitHub 上合并 PR；接受残余风险；修改仓库设置 | — |
| 调度会话 | 1 个，主检出，停在 `main` | 维护在途条目清单；判定能否并行；为条目和审计开会话；排定合并顺序与实验时段；合并后通知其他条目 | 不写功能代码，不推送 `main`，不合并 |
| 条目会话 | 每个条目 1 个，独立 worktree 与分支 | 用 `/aclt-plan` 出计划卡；批准后实现、验证、推送、开 PR；处理审计发现；用 `/aclt-sync` 做合并前同步 | 不改计划卡文件集之外的文件（先改卡），不审计自己的条目 |
| 审计会话 | 每次审计 1 个新会话，只读 | 用 `/aclt-audit` 按计划卡和仓库规则审计 PR，本次复跑检查，在 PR 上发表结论 | 不修改、提交或推送仓库内容，不继承条目会话的上下文 |

一个工作目录同一时间只由一个写入会话操作（ENV-1 §6）。

条目 worktree 放在 `.claude/worktrees/<名称>/`。该目录已被 `.gitignore` 排除，也不在交付清单的源目录内。手动创建时，从最新 `origin/main` 开分支，并且不跟踪上游：

```sh
git fetch origin
git worktree add --no-track -b <type>/<topic> .claude/worktrees/<名称> origin/main
```

首次推送使用 `git push -u origin <type>/<topic>`。

### 3.1 多代理协作（2026-11-14 补充）

条目会话和审计会话可以由 Claude Code、Codex 或其他编码代理承担，规则相同：

- **执行步骤：** 不支持 `/aclt-*` 技能的代理，直接读取 `.claude/skills/<名称>/SKILL.md`，按其中的步骤执行。其中的 `/code-review` 换成该代理自己的代码审查，并在审计结论中注明用了什么审查方式。
- **审计独立：** 审计不得由实现该条目的代理承担，优先由另一种模型的代理承担。审计评论在结论表之前写明实现代理与审计代理。

## 4. 授权范围

维护者于 2026-11-14 批准以下长期授权。授权持续有效，直到本文被修订或撤销。

| 会话 | 预先授权 | 仍须维护者逐次确认 |
|---|---|---|
| 条目会话 | <ul><li>计划卡经维护者在会话中批准后，创建对应的 GitHub Issue</li><li>在本条目分支上提交，并普通推送该分支</li><li>创建 draft PR；审计无未关闭的 `BLOCKER`/`MAJOR` 后，标为 ready</li><li>新建并推送指向本条目证据提交的 `evidence/*` 标签</li><li>为本条目发现或被报告的理论缺口新建 `theory-gap` Issue，并在本条目的计划卡和 PR 中引用（第 5.6 节）</li></ul> | <ul><li>计划卡本身</li><li>扩大文件集或目标</li><li>物理双机与 B 机操作（仍按 DUALHOST-SSH-1）</li></ul> |
| 审计会话 | <ul><li>读取仓库与 GitHub</li><li>在被审 PR 上发表审计评论</li></ul> | 任何其他写入 |
| 调度会话 | <ul><li>读取仓库与 GitHub</li><li>新建条目会话或审计会话</li><li>向会话转达维护者的指示，以及审计报告的理论缺口</li></ul> | 关闭 Issue 或 PR；登记 `theory-gap` Issue |
| 仅维护者 | <ul><li>合并 PR</li><li>修改仓库设置与标签</li><li>删除或移动远端分支、标签</li></ul> | — |

任何会话都不得做以下事情：

- 推送 `main`；
- force push；
- 对已推送的分支执行 rebase、amend 或 reset 后再推送；
- 使用 `git add .`；
- 关闭 SSH 严格主机密钥检查；
- 把凭据、真实 IP、用户名或本地路径写入仓库、Issue 或 PR。

## 5. 条目生命周期

### 5.1 规划（`/aclt-plan`）

条目会话在修改任何文件前完成规划。

1. 读取以下文件：
   - AGENTS.md 指定的文件
   - 本文
   - [当前状态](../07-roadmap/current-status.md) §7
   - 相关 OQ
2. 记录 `origin/main` 的 SHA。
3. 查看在途条目：开放的 `work-item` Issue、开放 PR，以及 `git worktree list`。

计划卡的字段与 [Issue 模板](../../.github/ISSUE_TEMPLATE/work-item.md)一致：

| 字段 | 要求 |
|---|---|
| 条目与来源 | OQ 编号，或当前状态 §7 中的优先项；一句话目标 |
| 基线 | 规划时 `origin/main` 的完整 SHA |
| 目标与非目标 | 非目标写明本条目不碰什么 |
| 文件集 | 预计修改或新增的路径；热点文件（第 6.2 节）单列 |
| 依赖 | 必须先合入的条目 |
| 验证计划 | 本次要运行的 make 目标；是否需要多虚拟机、物理双机或 B 机时段 |
| 理论依赖 | 本条目依赖、但尚无模型、推导或估计支撑的性质，以及对应的 `theory-gap` Issue；没有就写“无”（第 5.6 节） |
| 文档同步 | CONTRIBUTING §7 中适用的行；当前状态 §8 是否要求更新 |
| 验收标准 | 可检验的条目，审计逐条对照 |
| 不得宣称 | 本条目证据不支持的结论 |
| 分支 | `docs/`、`fix/` 或 `feat/` 加主题 |
| 并行判定 | 可并行 / 排队 / 需排期（第 6.1 节） |

维护者在会话中批准后，条目会话创建带 `work-item` 标签的 Issue，再开分支。判定为“排队”时，只建 Issue，不开分支。

### 5.2 实现

- **文件范围：** 只修改计划卡文件集内的文件。需要扩大时，先更新 Issue 中的计划卡，再通知调度会话，由调度会话重新判定并行冲突。
- **热点文件：** 对热点文件的修改集中在最后一个提交里，便于合并前同步时单独处理。
- **测试：** 测试结果必须来自本次执行，写明命令、退出码和基线。不得用历史通过记录代替。
- **提交：** 提交说明使用 CONTRIBUTING §6 模板，并逐个添加文件。代理不加 `Signed-off-by`，DCO 由维护者在合并时签署（CONTRIBUTING §11）。
- **证据标签：** 证据摘要钉住的提交，在推送前打标签（第 6.3 节）。
- **PR：** 推送后创建 draft PR，正文写 `Closes #<Issue>`，并通知调度会话。

### 5.3 审计（`/aclt-audit`）

调度会话为 PR 新开审计会话，审计按第 7 节进行，结论以 PR 评论发布。

存在 `BLOCKER` 或 `MAJOR` 时，退回条目会话修复。修复后，审计会话只审上次审计的提交之后的增量，并复核未关闭的发现项。

不再有未关闭的 `BLOCKER` 或 `MAJOR` 后，条目会话把 PR 标为 ready。

### 5.4 合并前同步（`/aclt-sync`）

调度会话按审计完成的顺序，指定下一个合并的 PR。该条目会话按以下步骤同步：

1. 把最新的 `origin/main` **merge** 进本分支，不使用 rebase。原因有三：merge 不改写已被证据钉住的提交；不需要 force push；squash 合并后 `main` 仍是线性历史。
2. 按第 6.2 节处理冲突。
3. 重新生成清单。
4. 本次重跑 `make check`。如果同步带入了代码、测试或 `Makefile` 的变化，改为运行 `make test`。
5. 推送，并确认 CI 通过。

如果同步带入的变化落在本条目文件集内的非热点文件上，请审计会话补审这次同步提交。

### 5.5 合并与收尾

维护者在 GitHub 上 squash 合并，并在合并提交说明末尾加上自己的 `Signed-off-by`（DCO，CONTRIBUTING §11）。之后由调度会话收尾：

1. 通知其他在途条目 `main` 已经前进。它们在轮到自己合并时再同步，不需要立即同步。
2. 确认 Issue 已由 `Closes` 关闭，证据标签已在远端。
3. 条目会话结束后清理对应 worktree。远端分支已由 GitHub 删除；本地分支在确认没有未推送提交后再删除。

### 5.6 理论缺口（2026-11-14 补充）

理论缺口指：实现、验收标准或证据依赖了某个性质，但这个性质背后没有模型、推导或估计。例如：

- 补算预算依赖的故障率；
- 分布式执行与单节点执行之间的成本关系；
- 计划改动后复用已有证据的条件；
- 交接时只有一个写者的安全性。

维护者负责理论缺口的数学建模。各角色发现缺口后的职责不同：

| 发现者 | 做什么 |
|---|---|
| 条目会话（规划或实现中） | 按下面第 1 步登记，并在本条目的计划卡和 PR 中引用 |
| 审计会话 | 不登记，在审计评论中列出缺口：出处、依赖的性质、所需数学对象、阻塞范围，以及分级（第 7.1 节）。由被审条目的条目会话登记并回填引用，审计会话在增量审计中核对 |
| 调度会话 | 不登记，转交相关的条目会话登记；没有相关条目时报告维护者，由维护者登记或指定登记者 |

1. **登记。** 先用 `gh issue list --label theory-gap --state all` 查找描述同一性质的 Issue。已有的，直接引用，并在该 Issue 下补充本条目的出处与阻塞范围；没有的，按 [理论缺口模板](../../.github/ISSUE_TEMPLATE/theory-gap.md) 新建带 `theory-gap` 标签的 Issue，写明：
   - 出处：文件与行号，或报告；
   - 依赖的性质；
   - 需要什么数学对象：待证命题、待估参数，还是模型；
   - 阻塞了哪项验收或闭合条件；
   - 相关的 OQ 或 CLM 编号。

   然后在计划卡的“理论依赖”字段和 PR 的“理论缺口”一节中引用这个 Issue，并通知调度会话；调度会话转告维护者。
2. **停止或继续。** 登记只是第一步，PR 必须写明每个缺口属于下面哪一种，以及适用范围：
   - **阻塞：** 条目的验收依赖这个缺口。相应的验收部分停下，等维护者给出模型或决定；PR 写明停下了哪些验收标准。不依赖它的部分可以继续。
   - **不阻塞：** 条目的验收不依赖这个缺口。可以继续，但把依赖它的结论标为 `ASSUMPTION`，并链接 Issue；PR 写明标记所在的文件与位置。
3. **禁止事项。** 代理不得自行建模，不得为了让测试或验收通过而挑选参数、阈值或近似，也不得自行决定用实测结果代替所需的推导；后者只能由维护者按第 4 步判定。代理可以整理事实、实测数据与已有文献，供维护者参考。
4. **关闭。** `theory-gap` Issue 只能由维护者关闭，关闭时在 Issue 中写明采用以下哪种结论：
   - **建模解决：** 维护者给出模型或推导，按 CONTRIBUTING 的证据分层落到相应的规范、分析或 OQ 中。
   - **作为经验证据接受（2026-11-14 补充）：** 维护者判定该性质不必证明，以实测作为证据。适用条件：
     - 该性质是实验条件，而不是协议性质，协议的正确性不依赖它；
     - 证据是实际测量或实际运行得到的，不是常量或推算；
     - 每次运行都能检出该性质不成立的情形，并会报错失败，而不是静默通过。

     结论必须写明适用范围（工具版本、配置、规模等），不得外推到范围之外。条目把相应的 `ASSUMPTION` 标记改为“经验证据（限某范围），见 #N”。

## 6. 并行规则

### 6.1 能否并行

- **文件集：** 两个条目的文件集，除热点文件外互不相交，才能同时开发。修改同一核心模块（例如同一实验的作业实现）的条目要排队。
- **依赖：** 依赖未合入条目的工作，等依赖合入后再从 `main` 开分支，不在未合入的分支上叠分支。
- **共享资源：** 需要多虚拟机、物理双机或 B 机运行的条目，由调度会话排期（第 6.4 节）。
- **数量：** 同时在途的条目建议不超过 3 个。瓶颈在于维护者的批准与合并，以及本机运行 `make test` 的资源。

### 6.2 热点文件冲突

| 文件 | 处理 |
|---|---|
| `SINGLEHOST-SHA256SUMS`、`WORKFLOW-SHA256SUMS` | 生成物，不手工合并。先取任一侧，解决其他冲突后运行 `make manifests` 并审阅 diff |
| `docs/07-roadmap/current-status.md` 状态日志 | 双方的行都保留。沿用新行插在表头之后的做法，后合并的条目的行放在上方。不改他人的行 |
| `current-status.md` 文末日期小节 | 双方小节都保留，按合并先后排列 |
| `docs/README.md` 索引、`Makefile` 目标 | 取并集；同步后 `make check` 必须通过 |
| 按行归属的共享表格，例如 `docs/07-roadmap/minimal-verifier-baseline.md` 的闭合条件表 | 每个条目只改计划卡中写明的行；双方的行都保留，不改他人的行。两个条目只在这类表格的不同行上重叠时，不算 §6.1 的文件集相交 |
| 其他文件 | 中止同步（`git merge --abort`），交调度会话处理。出现这种冲突，说明文件集判定有误 |

### 6.3 证据提交与标签

证据报告或摘要钉住的提交，在 PR 合并前打标签 `evidence/<YYYYMMDD>-<topic>` 并推送。标签只新建，不移动，也不删除。PR 正文列出标签名。

这样 squash 合并后，该提交仍能通过标签取得。CI 的完整克隆（`fetch-depth: 0` 会取回标签）也能读取它。

### 6.4 共享实验资源

多虚拟机、物理双机或 B 机的运行由调度会话排期。同一宿主或同一台 B 机，同一时间只运行一项。运行前先取得宿主级的锁，例如：

```sh
flock "${XDG_RUNTIME_DIR:-/tmp}/aclt-experiment.lock" make test-minimal-verifier-multivm ...
```

证据运行期间，不在同一宿主上并行运行 `make test`；无法避免时，在证据中记录并发负载。本地 `make check` 可以在多个 worktree 中并行运行。

## 7. PR 审计

审计会话只读，并遵守审计程序第 3 节的要求：固定基线、读写分离、不夸大结论、保留失败证据。

### 7.1 检查范围

1. **计划符合度**
   - 把实际改动的文件与计划卡的文件集比对。
   - 逐条核对验收标准。
   - 确认非目标没有被触碰。
2. **仓库规则**
   - CONTRIBUTING §9 的审查问题，以及 §7 同步矩阵。
   - 当前状态 §8 规定的更新义务。
   - 措辞是否越界：候选结论写成事实；VM 证据当作物理双机证据；历史通过当作本次结果。
   - 是否删除或改写了历史证据。
   - 是否写入了凭据、真实 IP、用户名或本地路径。
   - 理论缺口（第 5.6 节）：依赖的性质是否都有模型、推导、估计，或者已登记为 `theory-gap` Issue；对已登记的缺口，按它所处的状态核对：
     - **未决、阻塞：** 相应验收已停下，没有被声明通过。
     - **未决、不阻塞：** 依赖它的结论在写明的位置标了 `ASSUMPTION`，适用范围与实际依赖一致。
     - **维护者已关闭、建模解决：** 引用了维护者给出的模型或推导及其落点，依赖它的结论与之相符。
     - **维护者已关闭、作为经验证据接受：** Issue 中有维护者的关闭决定，并且已实际关闭；证据是实测或实际运行得到的；每次运行都能检出该性质不成立的情形并报错失败；`ASSUMPTION` 已改为“经验证据（限某范围），见 #N”，且引用的结论没有超出维护者写明的适用范围。

     以下情况判为 `MAJOR`：未登记的缺口；只有 Issue 链接而依赖它的验收仍被声明通过；为通过验收而挑选参数或近似；Issue 仍为未决，却按“已关闭”处理（例如去掉了 `ASSUMPTION`，或写成经验证据）；经验证据的引用超出写明的范围。审计会话不登记 Issue，把发现的缺口写入审计评论，由条目会话登记。
3. **代码正确性**
   - 有代码改动时，运行 `/code-review`，逐项核实它的发现后再采纳。
4. **本次复跑**
   - 在 PR 头部提交上运行 `make check`；代码、测试或 `Makefile` 有改动时，运行 `make test`。
   - 运行清单校验和 `git diff --check`。
   - 核对证据标签可达。
   - 多虚拟机与双机实验默认不重跑：用离线检查器核对保留的证据，并在结论中写明“未重跑”。

### 7.2 结论格式

审计评论包含以下内容：

- PR 头部 SHA、`origin/main` SHA、审计时间与时区；
- 本次执行的命令与退出码；
- 下表的分项结论；
- 发现项。

| 维度 | 允许值 |
|---|---|
| 计划符合度 | `PASS` / `FAIL` |
| 语义连续性 | `PASS` / `FAIL` / `BLOCKED` |
| 结构完整性 | `PASS` / `FAIL` |
| 历史隔离 | `PASS` / `FAIL` / `NOT_APPLICABLE` |
| 本次复跑 | `PASS` / `FAIL` / `NOT_RUN` |

**发现项编号：** `PRA-<PR号>-<NN>`，与审计程序的 `AUD-` 编号分开。

**分级：** 沿用 `BLOCKER`、`MAJOR`、`MINOR`、`NOTE`。

**状态：**

- `OPEN`
- `FIXED_IN_PR`：经审计会话复核后
- `ACCEPTED_BY_MAINTAINER`：须维护者在 PR 中明确接受

合并前不得标记为 `CLOSED_ON_MAIN`。

**结论：** 结尾写“建议合并”或“退回修改”，并列出“禁止宣称”，即本 PR 证据不支持的结论。审计结论只是建议，合并决定属于维护者。

## 8. 采用步骤

1. 本文合入 `main`。
2. 维护者创建 `work-item` 标签。
3. 主检出切回 `main`，作为调度会话。主检出上未推送的特性分支，先推送并开 PR，或移入独立 worktree。
4. 盘点已合并 PR 留下的本地特性分支。先给被证据钉住的提交打 `evidence/*` 标签并推送（清单经维护者确认），再清理这些本地分支。
5. 仓库公开后启用分支保护：要求 CI 通过，并要求合并前与 `main` 同步。届时第 5.4 节由 GitHub 强制执行，本文同步修订。
6. 维护者创建 `theory-gap` 标签（2026-11-14 补充）。

## 9. 本流程的变更

修改本文按普通的 `docs/` 条目进行，并须经维护者批准。第 2 节的事实发生变化时，应同步修订相应规则。这些事实包括：仓库设置、分支保护、热点文件分布、实验端口。
