# ACLt 设计原则

> 文档状态：规范性设计约束  
> 更新日期：2026-08-21
> 适用范围：协议、参考实现、仿真、文档与维护流程

## 1. 使用方式

本文件定义 ACLt 的顶层设计约束。具体算法可以迭代，但不得在没有架构决策记录、威胁模型更新和兼容性分析的情况下破坏这些原则。

关键词 `MUST`、`MUST NOT`、`SHOULD`、`SHOULD NOT` 和 `MAY` 的含义见 `terminology.md`。

SemanticStatus 与指定 ConformanceTarget 的 VersionDisposition 必须分别记录。设计被列为 V1 `CORE` 不代表其算法、证明、实现或测试已经完成；详细规则见 ADR-0003。

## 3. DP-01：如无必要勿增实体

若一项职能能够由公开、确定、版本化且可验证输入输出的协议算法完成，则不得仅为了叙述方便而创建新的身份、组织、中介或信任根。

新增实体必须同时证明：

1. 该职能确实不可缺少；
2. 现有 Principal 或 permissionless function 无法合理承担；
3. 新实体的权限、责任、失效影响和退出方式已经定义；
4. 引入后的净风险和净行政成本优于不引入；
5. 对应 ADR、威胁模型和权限测试已经建立。

因此，Broker、Planner、Scheduler、Verifier、Sampler 和 Aggregator 默认是函数，而不是协议固定角色。基金会、委员会、公共链和治理代币同样不因常见而自动成为必要组件。

## 4. DP-02：承诺主体与函数分离

Principal 必须能够持有密钥、签署消息、承担义务并接收权利。当前只有 `Requester` 与 `Provider` 满足不可约减条件。

函数描述“做什么”，Principal 描述“谁对承诺负责”。同一 Principal 可以在不同时间执行多个函数；多个标识也可能由同一现实控制者掌握。协议不得从函数名称推导特殊权限，也不得从标识数量推导独立性。

## 5. DP-03：协议与实现分离

ACLt 协议由以下内容构成：

- 规范化对象和字段语义；
- 状态机、前置条件与状态转换；
- 不变量和终态；
- 版本、兼容性和升级规则；
- 可验证的输入输出约束。

Control Plane、数据库、消息队列、对象存储、签名日志和区块链属于实现。任何实现都必须通过相同的适配器一致性测试，且不得把自身特性提升为未经声明的协议安全假设。

ACLt Abstract Machine、Logical Object Memory 和 Compile pipeline 是协议抽象，不是实现产品或新增 Principal。RPR 是可替换运行时边界，Host OS 是外部实现环境；二者不得反向定义 RIR 或 Task 的规范结果。

## 6. DP-04：先承诺，后观察

以下内容必须在观察相关执行或验证结果之前冻结：

- `ComputeReceipt` 的任务语义；
- `ProtocolVersion`；
- 验证类型、误差目标与终态规则；
- 有限总体、排除项、分层、相关性处理与随机性承诺；
- `Nmax` 的总体、预算和政策来源；
- `FundingPolicy` 与 `SettlementPolicy`。

任何实质修改必须产生新版本、新对象或追加式更正事件，不得静默覆盖原承诺。

## 7. DP-05：不确定性必须显式化

`TRUSTED` 只表示在预声明任务语义、证据、误差目标、相关性模型和资金边界下满足停止条件，不表示绝对正确。

当证据不足、总体无效、相关性无法安全处理、验证器不可用或预算达到上限时，协议必须输出 `UNRESOLVED` 或其他准确终态。维护者、Requester 或多数 Provider 均不得以人工意见覆盖这一结果。

## 8. DP-06：先限制损失，再讨论激励

协议安全不能只依赖“攻击成本大于收益”。ACLt 必须先使用以下硬约束限制最坏损失：

- 每个 Provider、相关集群、任务和时间窗口的暴露上限；
- 并发、任务价值、Lease、尝试和验证抽样上限；
- 任务级和全局资金上限；
- 最多一次终态与最多一次结算；
- 迟到结果隔离与旧 epoch 拒绝。

只有在攻击、时间窗口、外部收益和成本均被明确建模时，经济分析才可作为补充安全论据。

## 9. DP-07：证据不等于权威

ACLt 采用：

$$
PerformanceEvidence
\rightarrow CapabilityEstimate \pm Uncertainty
\rightarrow ExposureDecision
$$

历史证据用于估计某个 Principal 在特定任务族和条件下的履约能力。估计结果必须带有不确定度、有效期和证据版本，并仅用于具体任务的风险暴露决策。

协议中不得存在独立的 `Rank`、`ReputationState`、`VerifierAuthority` 或类似权威对象。能力证据、FoundationReport、维护报告或付款记录不得直接产生验证票权、最终审计权、治理权或结算裁决权。

## 10. DP-08：不假定身份独立

一个现实控制实体可以拥有多个标识、设备和账户。共同所有权、资金、网络、硬件映像、软件栈和协调行为都可能构成相关性证据。

未知相关性不得默认填为零。协议必须采用保守处理，例如相关集群上限、单集群权重上限、有效样本折减或最坏情形敏感性分析。具体算法目前仍是 `CANDIDATE`，但“不把身份数当独立样本数”已经确定。

## 11. DP-09：零抵押不等于零约束

普通 Provider 不需要为首次参与支付前置抵押，也不应因拒绝一个尚未接受的任务受到惩罚。

零抵押设计通过以下方式限制外部性：

- 新 Provider 的初始暴露较低；
- 单任务价值与同时在途任务数量受限；
- Lease 有明确期限且可恢复；
- 失败与迟到结果可归责但不会无限放大；
- 后续暴露随任务特定证据和不确定度调整；
- 所有探索仍处于硬损失上限内。

该原则不意味着 Sybil 问题消失，也不保证零成本身份具有独立性。

## 12. DP-10：失败、恢复和资源必须有界

活性声明必须附带网络、时钟、存储和故障假设。ACLt 在任意异步故障下的无条件完成不属于当前主张。

每个任务必须具有 deadline、最大尝试、Lease 期限和验证上限。新的 Lease epoch 必须严格递增；旧 epoch 的结果不得覆盖当前状态或产生新权利。达到边界后必须进入明确终态，而不是无限重试。

## 13. DP-11：资金来源与安全机制解耦

`FundingPolicy` 可以选择 Requester 费用、储备、补贴、可选发行或显式组合。资金来源是政策选择，不是验证证据，也不证明系统安全。

所有来源都必须预声明、可归责并受硬上限约束。执行、验证、存储、规划、退款储备和平台费用必须可区分。资金耗尽不得由未声明的临时发行掩盖。

## 14. DP-12：维护最小权限

维护边界负责规范、测试、参考实现、发布、漏洞响应和兼容性，不负责运行时个案裁决。

维护者不得修改冻结 Receipt、改变已开始验证的采样或权重、覆盖终态、制造结算，或把维护意见作为优先证据。维护产生的修复只能作用于未来版本，或以追加式更正形式保留原始历史。

## 15. DP-13：全链路可审计与可重放

关键对象必须绑定明确的 `ProtocolVersion`、规范化摘要和因果引用。所有可归责事件应以追加方式记录；错误更正必须产生新事件并指向被更正记录。

实现必须能够从合法事件重放协议状态，并证明并发、重试、崩溃恢复或存储适配器替换不会破坏终态唯一性、结算幂等性和资金守恒。

## 16. DP-14：对任务语义诚实

验证必须针对任务类型定义。确定性重执行、解析式检查、抽样检查、冗余比较和未来可验证计算具有不同的前提与错误模型，不得被统一包装为同一种证明。

如果任务没有已注册且满足要求的验证方式，协议必须在创建阶段拒绝，或将其标记为 `UNSUPPORTED`。不得用一般多数票掩盖任务语义不可判定或验证器缺失。

## 17. DP-15：保留安全退出

安全系统必须允许诚实地承认失败或不确定。ACLt 的正常设计包括 `UNRESOLVED`、`FAILED`、`EXPIRED` 和 `FUNDING_EXHAUSTED`，这些状态不是异常补丁。

每种终态必须具有唯一、可审计的严格含义，并在 `SettlementPolicy` 中预声明权利、费用、退款和故障归因。任何终态都不得自动解释为绝对正确性证明。

## 18. DP-16：前端不定义协议执行语义

协议必须在机器/网络可交换层绑定可验证的执行语义，而不能把某个源语言、编译器版本或本机二进制当作规范。V1 采用 RIR 作为该规范表示，Rust Profile 作为参考前端；未来 C++23 等前端只能通过降级到同一 RIR 并满足相同 validator、effects、resource 和结果语义进入兼容范围。

V1 通过 RPR 执行规范 RIR。Logical Object 是显式输入输出；Host OS 文件、网络、时钟、随机性、环境变量和设备状态默认不可见。Compile 的 Lowering、Decomposition 和 Packing 都必须可审计，且不得扩大 Receipt 绑定的任务义务。

该原则不证明 RIR、编译器或运行时正确，也不证明程序结果确定。RIR 编码、validator、lowering、runtime、资源计量和跨实现差分测试仍是 G0/G1 证明义务。V1 未支持或未验证的能力必须被拒绝或标为 `UNSUPPORTED`，不得静默回退到宿主原生语义。

## 19. DP-17：工程事实分层闭合

ACLt 不要求用形式证明覆盖所有现实世界事实。每项要求必须区分：结构闭合、算法闭合、来源忠实性和部署风险接受。前两者由 Schema、确定算法、定理和对拍测试承担；后两者由版本化组件引用、追加日志、权限隔离、故障注入、实现审计、有效期和损失预算承担。

工程证据不得反向改变协议数学：它不能把未知身份变成独立身份，不能让维护报告进入真理权重，也不能在观察结果后改变统计参数。工程假设未建立或被撤销时，相应能力必须 `DISABLED`、`AUDIT_ONLY` 或 fail closed，而不是阻止不依赖该假设的接口、validator 和测试继续实现。

官方主网可以通过版本化 assurance 声明其接受的 Profile、RPR、validator、日志后端、相关性策略和风险预算；该声明只适用于绑定网络和组件，不自动延伸到主网外。详细决定见 [`../05-decisions/ADR-0005-engineering-assumptions-and-mainnet-assurance.md`](../05-decisions/ADR-0005-engineering-assumptions-and-mainnet-assurance.md)。

## 20. 新设计的准入检查

任何新增对象、角色、算法或基础设施都应回答：

1. 它解决的具体问题和失败模式是什么？
2. 它属于 Principal、function、protocol object、implementation 还是 maintenance？
3. 是否能通过现有公开函数完成而无需新增实体？
4. 它引入哪些权限、信任假设、行政成本和单点故障？
5. 它改变哪些不变量、冻结点、终态或资金边界？
6. 在 Sybil、串谋、重放、分区、崩溃和资金耗尽下会怎样？
7. 哪些主张可以被测试、证明或反驳？
8. 是否提供迁移、撤销、兼容和安全退出路径？
9. 若涉及执行语言或硬件，是否保持同一 RIR、effects、资源与结果语义？
10. SemanticStatus 与各 ConformanceTarget 的 VersionDisposition 是否分别记录，且 CORE 缺口是否仍被列为 Gate 阻断？
11. 该要求属于结构、算法、来源忠实性还是部署风险接受？证据类型是否与主张匹配？

不能明确回答这些问题的设计，不应进入协议核心。
