# ACLt Protocol 威胁模型

> 文档状态：G0 安全需求基线  
> 更新日期：2026-08-18  
> 适用范围：协议规范、参考实现、适配器、仿真与维护流程  
> 配套文档：[系统不变量](invariants.md)

## 1. 文档目的

本文件规定 ACLt Protocol 当前必须考虑的攻击者、故障、受保护资产、信任边界、必要控制和剩余风险。它回答“系统必须防止什么或将其损失限制到什么范围”，但不声称当前设计已经完成形式化证明、工程验证或公共网络实证。

本威胁模型遵守以下边界：

- 只有 `Requester` 与 `Provider` 是不可再约减的 Principal；
- `Plan`、`Admit`、`Schedule`、`Execute`、`Sample`、`Verify`、`Aggregate`、`Settle` 和 `UpdateEvidence` 是 permissionless functions，不是固定特权身份；
- Protocol 是规则集合，不是行为者；Control Plane、数据库、日志或区块链是实现；
- Maintenance 是最小权限边界，不是运行时裁判；
- Provider 标识数量不等于独立控制实体数量；
- `TRUSTED` 是条件性协议结论，不是绝对正确性证明；
- 安全首先依赖硬边界和安全终态，经济激励只作为补充控制。

## 2. 安全目标

| ID | 安全目标 | 严格含义 |
|---|---|---|
| SG-01 | 任务语义完整性 | 同一 `ReceiptID` 永远只绑定同一规范化任务、版本、验证、资金和结算语义 |
| SG-02 | 状态转换安全 | 只有满足版本、签名、前置状态和不变量的函数输出才能改变协议状态 |
| SG-03 | 有界风险暴露 | 单个 Provider、相关集群、Receipt 和时间窗口的并发、价值、尝试和最大损失受硬上限约束 |
| SG-04 | 执行隔离与可恢复性 | Lease、epoch、deadline、attempt 和 checkpoint 阻止无限占用、迟到覆盖和无界重试 |
| SG-05 | 条件性验证可靠性 | 只有在预声明任务语义、总体、抽样、相关性模型和停止条件成立时才能输出 `TRUSTED` |
| SG-06 | 显式不确定性 | 证据不足、验证无效或边界耗尽时安全进入 `UNRESOLVED` 或其他准确终态 |
| SG-07 | 资金与结算完整性 | 承诺、结算和退款储备不越过授权资金上限，且同一权利最多结算一次 |
| SG-08 | 证据完整性与可归责性 | PerformanceEvidence、VerificationEvidence 和 EventRecord 可追踪来源、版本、条件与更正历史 |
| SG-09 | 权限不扩张 | 履约能力、维护身份、付费能力或实现控制权不得自动转化为真理权、治理权或个案裁决权 |
| SG-10 | 实现语义一致性 | 更换数据库、日志、结算通道或账本后，外部可观察的协议语义和不变量保持一致 |
| SG-11 | 条件性活性 | 在明确的网络、时钟、存储、资金和诚实执行假设下，任务能够推进或进入安全终态 |
| SG-12 | 最小信息暴露 | 相关性分析、审计与归责只收集实现安全目标所必需的信息，并明确保留和访问边界 |

## 3. 受保护资产

| 资产 | 需要保护的性质 | 主要失效影响 |
|---|---|---|
| `ProtocolVersion` | 真实性、完整性、可解析性、兼容性 | 降级、规则分叉、错误状态转换 |
| `ComputeReceipt` / `ReceiptID` | 规范化语义不可变、内容可用 | 各方执行不同任务、预算或验证规则 |
| Principal 密钥与签名 | 真实性、授权范围、可撤销性 | 身份冒用、伪造 Lease、结果或结算 |
| `WorkPlan` / `Assignment` | 合法性、依赖完整性、资源边界 | 遗漏工作、重复计算、资源耗尽、错误合并 |
| `ExposureDecision` | 证据绑定、原子配额、有效期 | 并发超限、集中暴露、最坏损失失控 |
| `Lease` / `Attempt` / epoch | 单调性、唯一性、期限和归责 | 重放、双重执行、迟到覆盖、重复权利 |
| 程序、输入、结果、Checkpoint | 摘要完整性、可用性、环境绑定 | 错误执行、验证失效、恢复污染 |
| `EligibilitySnapshot` 与随机性承诺 | 预先冻结、不可偏置、可复算 | 选择性抽样、事后改总体、统计结论失效 |
| `VerificationEvidence` / `VerificationDecision` | 任务适用性、来源、相关性、唯一终态 | 错误背书、双终态、伪造确定性 |
| `FundingPolicy` / `SettlementPolicy` | 预声明、资金来源、上限、终态映射 | 隐性补贴、超额支付、争议或资金缺口 |
| `Settlement` | 唯一权利键、幂等性、资金守恒 | 重复支付、越权退款、超额承诺 |
| `PerformanceEvidence` / `EventRecord` | 追加性、因果性、更正可见 | 能力估计污染、历史改写、审计失真 |
| 维护发布与适配器 | 供应链完整性、最小权限、可撤销性 | 全局规则污染、后门、语义漂移 |
| 相关性与控制关系数据 | 准确性、最小化、隐私 | Sybil 折减失效或不必要的身份关联泄露 |

## 4. 信任模型

### 4.1 不默认信任

ACLt Protocol 不默认信任：

- Requester 提交的任务善意、合法、可执行或可廉价验证；
- Provider 的资源、环境、独立性、结果或故障声明真实；
- 多个 PrincipalID、Node、Account 或 Device 属于不同现实控制者；
- 执行某个 permissionless function 的 Principal 会正确执行函数；
- 单次 VerificationEvidence 或多数输出代表真理；
- Control Plane、数据库、对象存储、时钟、随机源、网络或结算通道永不故障；
- Maintainer、发布密钥或依赖供应链永不被攻破；
- 区块链、联盟账本或中心化数据库天然保持 ACLt Protocol 的语义；
- “攻击成本大于回报”在所有外部收益、破坏动机和时间窗口下都成立。

### 4.2 当前必要假设

每个实现必须明确声明并验证其实际依赖的假设。当前至少包括：

| 假设 | 要求 | 假设失效时的处理 |
|---|---|---|
| 密码学 | 选定签名、摘要和随机性方案在声明威胁等级下安全 | 拒绝验证、撤销版本或密钥；不得继续作安全背书 |
| 密钥控制 | Principal 对其签名密钥负责，撤销与轮换可被传播 | 标记密钥状态；阻止新承诺；保留既有事件证据 |
| 内容可用性 | 程序、输入、结果和证据在所需阶段可按摘要取得 | 拒绝推进、恢复或进入准确失败终态 |
| 时钟 | Lease、deadline 与有效期依赖明确的时间模型和容差 | 不满足时不得声称活性；不得接受含糊的迟到权利 |
| 网络 | 消息可能延迟、重复、乱序或丢失；恢复条件必须声明 | 依靠幂等、epoch、重试与安全终态，不假定实时同步 |
| 持久化 | 实现提供原子唯一约束、追加事件和可验证恢复 | 无法保证时停止提交终态或结算 |
| 任务验证器 | 每类验证方法只在其声明任务语义和错误模型内有效 | `UNSUPPORTED`、`UNRESOLVED` 或拒绝创建 |
| 随机性 | 抽样随机性在观察结果前承诺且可审计 | 抽样无效；不得输出 `TRUSTED` |
| 资金 | 所有可用来源、额度和最终性在任务前声明 | `FUNDING_EXHAUSTED` 或暂停结算，不得隐性借用 |
| 相关性信息 | 控制关联可能不完整且不可视为零 | 保守折减证据并收紧集群暴露上限 |

假设是安全结论的条件，不是系统已经证明的事实。

## 5. 攻击者与故障主体

| 主体 | 可用能力 | 主要目标 |
|---|---|---|
| 恶意 Requester | 提交畸形、昂贵、不可验证或恶意程序；谎报价值或构造结算争议 | 消耗资源、攻击 Provider、逃避付款、诱导错误结果 |
| 恶意 Provider | 虚报能力、接受后弃单、伪造结果/检查点/证据、选择性响应 | 获得未应得权利、降低成本、破坏任务 |
| Sybil/串谋集群 | 创建任意多个低成本标识；共享所有权、资金、网络、软件、硬件或输出 | 放大暴露、操纵验证、刷取履约证据或奖励 |
| 恶意函数执行者 | 对 Plan、Admit、Schedule、Sample、Verify、Aggregate 或 Settle 提交畸形输出 | 绕过规则、偏置抽样、扩大权利或制造错误终态 |
| 实现运营者 | 控制部分服务、数据库、队列、日志、时间或可见性 | 审查、重排、回滚、分叉或选择性提供状态 |
| 恶意/失陷 Maintainer | 控制发布流程、签名密钥、依赖或参考实现 | 植入后门、扩张权限、追溯改变个案 |
| 外部攻击者 | 窃取密钥、利用接口、网络或沙箱漏洞，实施流量和资源攻击 | 冒用、远程执行、泄露、拒绝服务 |
| 非恶意故障 | 崩溃、分区、时钟漂移、磁盘损坏、依赖中断、软件缺陷 | 造成与攻击相似的安全或活性后果 |

协议不能仅根据主观动机区分攻击与故障；关键控制必须针对可观察行为和状态结果生效。

## 6. 攻击者能力边界

在未由具体部署收紧之前，应按以下保守能力建模：

- 攻击者可以创建和控制多个 PrincipalID、Node、Account 与 Device；
- 多个 Requester、Provider 或函数执行者可以串谋并共享信息；
- 攻击者可以观察公开协议状态，并据此选择是否参与、何时提交或何时退出；
- 消息可能被延迟、重复、乱序、丢弃或重放；
- 攻击者可以提交格式正确但语义恶意的数据；
- 攻击者可以制造预算消耗、长尾执行、验证争议和资源枯竭；
- 攻击收益可以来自协议外部，包括竞争破坏、对冲头寸、政治或纯破坏动机；
- 攻击者可能控制一个实现组件，但不应因此获得超越协议前置条件的合法权力；
- 密钥、发布流程、依赖或执行沙箱可能被攻破，必须存在检测、撤销和限制影响面的机制。

不得假定存在固定诚实多数、固定最大 Byzantine 比例或 51% 安全阈值，除非未来某个具体子协议明确定义并证明对应模型。

## 7. 威胁登记表

### 7.1 任务、版本与规划

| ID | 威胁 | 可能影响 | 必要控制 | 不变量 | 当前状态 |
|---|---|---|---|---|---|
| TH-01 | Receipt 字段歧义、碰撞、静默修改或对不同参与者展示不同语义 | 各方执行、验证或结算不同义务 | canonical encoding；摘要覆盖全部实质字段；内容寻址；变化生成新 ReceiptID | INV-01、INV-02 | Schema 与编码仍为 `OPEN/P0` |
| TH-02 | 版本降级、未知版本、兼容性混淆或规则分叉 | 旧漏洞重现、不同状态机并行生效 | 所有活对象显式绑定 ProtocolVersion；版本兼容和撤销检查 | INV-02、INV-16 | 版本迁移仍为 `OPEN/P0` |
| TH-03 | 恶意、不可执行、侵权或资源炸弹任务 | Provider 或实现资源耗尽、法律与安全风险 | 创建期验证；资源/权限声明；执行沙箱；任务价值与预算硬上限；`REJECTED_AT_CREATE` | INV-09、INV-10 | 沙箱和任务策略为 `OPEN/P0/P2` |
| TH-04 | WorkPlan 遗漏依赖、重复工作、错误合并或人为制造极端碎片 | 错误结果、放大成本、无法恢复 | 确定性合法性检查；DAG、合并与失败语义；Plan 输出无特殊权 | INV-01、INV-09 | WorkPlan 规则为 `OPEN/P0` |

| TH-14 | 恶意任务突破沙箱、访问未授权数据或消耗宿主资源 | Provider 系统受损、数据泄露、横向移动 | 最小权限沙箱、资源配额、网络/文件策略、隔离和审计 | INV-09、INV-10 | 工程控制为 `OPEN/P0/P2` |

|---|---|---|---|---|---|

| TH-20 | 达到 Nmax 后继续采样、临时增资或人工覆盖结论 | 无界成本、规则追溯、伪造确定性 | Nmax 取总体/预算/政策最小值；边界后输出安全终态 | INV-09、INV-12、INV-15 | Nmax 算法为 `OPEN/P0` |
| TH-21 | 并发 Aggregate 产生两个 VerificationDecision | 双终态、双结算、审计分叉 | 原子终态提交；唯一约束；事务重试不得改变终态 | INV-04、INV-07 | 竞态模型为 `OPEN/P0` |

### 7.5 资金、结算与经济攻击

| ID | 威胁 | 可能影响 | 必要控制 | 不变量 | 当前状态 |
|---|---|---|---|---|---|
| TH-22 | 隐性借用、临时增发、跨资金桶挪用或虚假预算 | 掩盖真实成本、资不抵债、越权支付 | FundingPolicy 预声明来源与上限；资金桶分离；资金守恒 | INV-06 | 具体账务模型为 `OPEN/P0` |
| TH-23 | 重放、并发或超时恢复造成重复结算 | 超额支付和权利分叉 | 唯一权利键、幂等 Settle、最多一次 Commit | INV-05、INV-07 | 事务与唯一键为 `OPEN/P0` |

| TH-26 | 低成本身份反复进入、领取探索额度后退出 | 持续消耗探索预算和执行资源 | 每集群/窗口探索与损失上限；能力不确定度；异常证据分析 | INV-09、INV-10、INV-14 | 攻击仿真为 `OPEN/P1` |

## 8. 关键攻击路径

### 8.1 Sybil—证据刷取—暴露放大

1. 同一控制者创建多个 Provider 标识；
2. 使用低风险任务积累高度相关的 PerformanceEvidence；
3. 系统错误地把标识数当作独立证据或把历史表现压缩为 Rank；
4. 多个标识同时获得高价值任务或验证影响；
5. 攻击者集中弃单、伪造结果或串谋验证。

必须由 INV-10、INV-13 和 INV-14 联合阻断：证据保持任务与条件上下文、未知相关性保守处理、暴露按相关集群硬限制、能力不得转化为真理权。

### 8.2 结果观察—验证规则变更—错误背书

1. 执行者观察候选结果或初步验证意见；
2. 改变 EligibilitySnapshot、分层、排除项、相关性折减或停止阈值；
3. 只保留有利抽样并提前停止；
4. 将结论标为 `TRUSTED`。

必须由 INV-11 和 INV-12 阻断：总体和全部统计政策先于观察冻结，抽样不放回且可重放；任何承诺破坏都只能拒绝或进入 `UNRESOLVED`。

### 8.3 Lease 重放—迟到结果—重复权利

1. Assignment 在超时或分区后被重新签发；
2. 旧 Provider 在新 epoch 生效后提交旧结果；
3. 实现错误地覆盖当前状态或为两个 epoch 同时生成权利；
4. 并发结算重复支付。

必须由 INV-03、INV-05 和 INV-08 阻断：epoch 单调递增，旧结果只可作为审计证据而不能改变当前状态，同一结算权利最多提交一次。

### 8.4 维护更新—个案追溯—规则捕获

1. Maintainer 或发布密钥控制者观察到争议任务；
2. 发布或直接注入对该任务有利的新权重、验证或退款规则；
3. 修改历史状态或重新结算；
4. 将维护意见作为更高权证据。

必须由 INV-02、INV-12 和 INV-15 阻断：运行对象固定 ProtocolVersion，更新只作用于未来版本；维护者没有个案覆盖权；更正必须追加而非重写。

## 9. 拒绝服务与活性边界

ACLt Protocol 不承诺在任意异步网络、任意资源枯竭或所有执行者恶意时仍完成任务。活性必须写成条件命题，例如：

> 在内容可用、授权资金未耗尽、至少存在满足准入条件并最终响应的执行者、网络最终恢复到声明时延边界、时钟与持久化假设成立时，合法任务最终推进到下一状态或某个协议终态。

无条件活性不可作为当前安全主张。以下状态是预期的安全退出，而不是实现必须掩盖的错误：

- `REJECTED_AT_CREATE`；
- `FAILED_PLANNING`；
- `UNSUPPORTED`；
- `UNRESOLVED`；
- `FAILED`；
- `EXPIRED`；
- `FUNDING_EXHAUSTED`。

## 10. 隐私边界

Sybil 与相关性控制可能需要观察所有权、资金、网络、设备、软件栈或行为关联，但这些信息同时具有隐私风险。当前要求是：

- 只收集与明确风险决策有关的数据；
- 记录数据来源、置信度、用途、有效期和更正路径；
- 未知信息不得自动视为独立或无关联；
- 相关性结论不得自动转化为现实身份断言；
- 公开审计不意味着公开全部原始个人或设备数据；
- 访问、保留、聚合和删除政策必须在进入外部试点前规格化。

具体隐私模型、证明方式和法域要求仍为 `OPEN`。

## 11. 明确禁止的安全主张

在对应证明义务完成前，不得声称：

- ACLt Protocol 的整体鲁棒性已经得到证明；
- 任意计算都能以低成本可靠验证；
- 多个 Provider 代表多个独立控制实体；
- 51% 是 ACLt Protocol 的默认安全阈值；
- Rank、信誉或历史履约能够代表真理；
- `TRUSTED` 表示绝对正确；
- 零抵押消除了 Sybil 或弃单风险；
- 攻击成本大于协议内收益即可排除攻击；
- 验证资金可以通过临时发行变为“免费”；
- 区块链或去中心化存储会自动满足 ACLt Protocol 不变量；
- 中心化参考实现已经具备分布式容错；
- 未经证明的序贯方法保持 anytime-valid 误差控制。
- Rust 的语言安全、RIR 的存在或单一参考 compiler 自动保证结果正确、确定性、资源一致或分布式安全；
- V1 已支持 unsafe Rust、完整宿主 effects、原生执行、GPU/专用加速器或非确定性任务。

## 13. 威胁模型更新规则

发生以下变化时必须更新本文件：

- 新增 Principal、permissionless function、协议对象或特权组件；
- 改变 Receipt、验证、资金、结算、终态或维护边界；
- 引入公共链、联盟账本、TEE、零知识、交互式证明或新随机性来源；
- 改变 RIR、Rust Profile、conforming frontend、runtime、effects、资源模型或 V1 能力边界；
- 改变网络、时钟、持久化、结算或密钥假设；
- 发现新的串谋、Sybil、证据污染、预算耗尽或供应链攻击；
- 仿真、形式化验证、故障注入或外部试点否定现有假设。

任何新增实体都必须先证明现有 Principal 和公开协议函数无法承担其职能，并记录净安全收益、行政成本和新增信任根。

## 14. 验收条件

本威胁模型在 G0 阶段的最低验收条件是：

1. 每个核心对象、函数和信任边界至少映射到一个威胁；
2. 每个高影响威胁至少映射到一个硬控制或明确安全终态；
3. 所有硬控制均映射到 `invariants.md`、未来状态机或机器可执行策略；
4. `CANDIDATE`、`ASSUMPTION` 与 `OPEN` 项不得被描述为已证明；
5. 不存在依赖 Rank、51%、默认增发、固定诚实多数或区块链自动安全的隐含控制；
6. 并发、重放、分区、崩溃恢复、资金耗尽和维护滥权进入测试计划；
7. 剩余风险和禁止主张保持公开、可审计且可反驳。
