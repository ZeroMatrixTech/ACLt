## 1. 使用规则

本文件不是愿望清单。每个问题必须满足以下至少一项：

- 阻断某个验证门；
- 影响至少一条系统不变量；
- 改变信任、资金、最坏损失或运行时权限边界；
- 需要实验、证明、外部审查或法律判断才能收敛；
- 若不显式决定，不同实现将产生不兼容结果。

问题状态使用：

- `OPEN`：需要决定，尚无足够证据；
- `INVESTIGATING`：正在收集证明、实验、原型或外部意见；
- `BLOCKED`：关闭依赖尚未满足；
- `DECIDED`：已形成决定，并已同步至规范或 ADR；
- `CLOSED`：决定已经验证且关闭证据已归档；
- `SUPERSEDED`：问题被新的问题或设计替代；
- `REJECTED`：该路径不再采用，除非出现新证据。

这些值是 `IssueStatus`，不替代权威语义的 SemanticStatus，也不表示 V1 VersionDisposition。V1 的 `CORE/DEFERRED/REJECTED` 只在 [`../03-protocol/v1-profile.md`](../03-protocol/v1-profile.md) 登记。

优先级含义：

- **P0**：阻断 G0、公开发布，或存在未封顶的安全/资金风险。
- **P1**：阻断 G1—G4 的可信仿真、参考实现或恢复验证。
- **P2**：不阻断当前核心，可在核心稳定后评估。

“当前建议”只是下一步首选路径，不等于 `DECIDED`。只有关闭证据满足，并同步到规范或 ADR 后，状态才能改变。

## 4. OQ-02 — 规范对象、编码与版本演进

**问题。** 如何使 Task、WorkPlan、Assignment、Lease、Receipt、Evidence、VerificationSession、Settlement 等对象在不同实现中具有唯一可验证含义？

**备选路径。**

1. 模式：JSON Schema、Protocol Buffers、CBOR/CDDL、自定义 IDL，或用语义模型加多种绑定。
2. 规范编码：JCS/规范 JSON、确定性 Protobuf、规范 CBOR，或域专用二进制格式。
3. 标识：内容寻址；随机/时间有序 ID 加内容哈希；纯外部句柄。
4. 演进：严格主版本分叉；带能力协商的向前兼容；版本化对象族；显式迁移函数。
5. 扩展：拒绝未知字段；保留但不解释；命名空间扩展；功能位协商。
6. RIR：独立规范二进制/文本编码；复用对象编码；RIRVersion 独立演进；或与 ProtocolVersion 锁步演进。

**当前建议。** ADR-0003 已决定 SemanticStatus 与 VersionDisposition 分离，并把 V1 Profile 作为版本处置的唯一存储位置；该子问题不再开放。剩余工作是先写与传输格式无关的 Abstract Machine、Logical Object、规范对象和哈希域，再选择至少一种确定性绑定；RIR 必须具有独立可验证的 canonical encoding，并由 Receipt 无歧义绑定 ContractTuple/RIR Digest；所有影响合法性或签名的字段必须进入规范编码；扩展字段不得静默改变既有语义。

**关闭证据。** machine-readable SemanticStatus registry 与 V1 Profile join、Abstract Machine/Logical Object 字段表、必选/可选规则、规范编码测试向量、哈希域分离、ContractTuple 兼容矩阵、未知字段行为和至少两个独立编码实现的一致结果。

**依赖。** 无；这是多数 P0 问题的前置依赖。

## 5. OQ-03 — Principal、签名与控制关系

**问题。** 在只保留 Requester 与 Provider 两类不可约 Principal 的前提下，如何表达授权、密钥轮换、委托和同一控制主体下的多个身份？

**备选路径。**

1. 标识：裸公钥；DID；外部 PKI 主体；部署本地账户加可验证密钥。
2. 授权：单密钥；阈值签名；能力令牌；短期会话密钥；分层委托。
3. 轮换：连续签名链；外部注册表；延时恢复；多方恢复。
4. 控制关系：自我声明；经济绑定；网络/行为聚类；第三方证明；仅保守地视为未知相关。
5. 隐私：公开稳定标识；任务级伪名；可选择披露的关联证明。

**当前建议。** 协议只要求可验证授权和可追踪轮换，不绑定单一身份基础设施；把“身份唯一性”和“控制独立性”分开。V1 不再把“证明每个 ID 背后是不同自然人”作为关闭目标；官方主网使用可观察关联信号、相关性簇和暴露/损失上限，未知控制关系不能推定独立。

**关闭证据。** 签名责任矩阵、授权与撤销状态机、轮换测试向量、委托上限、控制关系进入风险模型的明确规则，以及隐私威胁评审。

**依赖。** OQ-02、OQ-08、OQ-13。

## 6. OQ-04 — WorkPlan、准入与 Assignment 合法性

**问题。** 谁都可以调用 Plan、Admit 和 Schedule 时，哪些规则使一个计划或分配成为确定、可复核且不越权的协议动作？

**备选路径。**

1. 计划生成：Requester 提供；Provider 提议；第三方规划器提议；多方案竞价；确定性参考规划器。
2. 准入：静态规则；资源报价约束；策略脚本；证明携带的计划；组合判定。
3. 调度：最低成本；能力下界；风险调整效用；多目标 Pareto；随机化探索。
4. 冲突：首个合法分配；显式排序键；租约竞争；提交—揭示；部署层共识。
5. 拆分：固定分片；自适应分片；冗余副本；DAG；不可拆任务。

**当前建议。** 使用 `Compile = Lowering + Decomposition + Packing`：Lowering 在 Receipt 冻结前产生并验证 RIR；Decomposition/Packing 在同一 Receipt 下形成候选 TaskGraph、WorkPlan 和 Assignment。将计划提议与计划合法性分开；任何主体都可提议，但相同冻结输入下合法性判断必须一致。调度目标可以实现特定，但暴露上限、资金上限和验证要求必须是协议约束。

**关闭证据。** Lowering/Decomposition/Packing Schema、TaskGraph/WorkPlan 约束语言、语义保持与合法性谓词、冲突排序、Assignment 前置/后置条件、资源超额和资金不足反例，以及 golden/differential vectors。

**依赖。** OQ-02、OQ-03、OQ-09、OQ-10。

**2026-11-14 M3 实验证据。** [物理双机基线验收](../testing/DUALHOST-BASELINE-20261114.md)在固定两片统计计划上核对分片位置、完整覆盖和答案与裁决的绑定。缺片与错绑均在离线归并入口被拒绝。OQ-04 的正式计划合法性条件继续为 `OPEN`。

**2026-11-14 M2 实验证据。** [多来宾容量排序通用契约验收](../testing/MULTIVM-SORT-CONTRACT-20261114.md)。固定 6/8 MiB 实例在通用契约下核对键范围覆盖和有序归并。同宿主三来宾完成交付，同规格单来宾对照实际写入失败。OQ-04 继续为 `OPEN`。

**2026-11-14 M9 实验证据。** [通用契约来宾验收](../testing/MULTIVM-CONTRACT-CLOSURE-20261114.md)。同一整题从树形计划切换到平铺计划后按目标槽位重新接纳冻结题目摘要相同的源证据。OQ-04 的正式计划准入继续为 `OPEN`。

## 7. OQ-05 — Lease、RIR 执行、恢复与沙箱

**问题。** 如何在崩溃、延迟、重复提交、资源滥用和不可信代码下执行任务，同时保持可恢复和至多一次的经济效果？

**备选路径。**

1. 租约：固定期限；可续租；基于逻辑 epoch；基于外部协调层高度；混合超时。
2. 重试：同 Provider 重试；换 Provider；投机并行；执行检查点迁移。
3. 提交：首次有效提交；最高 epoch；显式取消令牌；提交—揭示。
4. 沙箱：容器；微虚拟机；WebAssembly；TEE；任务专用隔离；外部受信执行环境。
5. 资源计量：Provider 自报；Control Plane 观测；可验证计量；预付上限；多方观测。
6. 数据访问：完整复制；按需拉取；能力令牌；数据本地执行；加密/密封输入。
7. 执行表示：**已决定 V1 使用 RIR，Rust Profile 为 reference frontend**；仍需在文本/二进制编码、类型系统、effects、资源计量、错误与 checkpoint 语义之间收敛。
8. 前端：仅 Rust Profile；未来 C++23/其他 conforming frontend；或多前端同时进入 V1。当前决定为首项，后两项延期。

**当前建议。** 协议使用不可变 Logical Object 输入，定义 Lease proposal → Provider accept → active Lease、epoch、幂等键、过期和结果接受规则；V1 只由 RPR 执行 Receipt 绑定且通过 validator 的 RIR，Rust Profile 负责 reference lowering。active Lease 是执行 scope/RPR/environment/resource tuple 的唯一授权，派生 `ExecutionCapability` 供 Dispatch 与 RPR 分别校验；不新增第三份 Dispatch scope。沙箱与计量可以采用不同部署机制，但必须满足冻结的 runtime/effects/resource Profile。经济结算应绑定接受的 Receipt 和 active Lease，而非绑定“进程是否曾运行”。

**关闭证据。** Logical Object Schema/可用性、RIR grammar/canonical encoding/validator、Rust Profile 允许与禁止构造、lowering golden vectors、RPR capability ABI、runtime/effects/resource/error semantics、ExecutionCapability golden vectors、Dispatch/RPR 旁路与换环境测试、执行状态机、重复/迟到/分区测试、资源耗尽与逃逸威胁测试、恢复目标、Receipt 幂等性和故障注入结果。

**2026-10-23 进展。** 项目决定 RIR 主体采用确定性 Wasm 核心子集，不自研指令集。子集、规范编码、计量、结果分类与宿主 ABI 的候选条款见 [ADR-0006 草案](../05-decisions/ADR-0006-rir-deterministic-wasm-core-subset.md)，状态 `PROPOSED`；其中 RIRVersion 独立演进也回应 OQ-02 第 6 项。OQ-05 仍为 `OPEN`，直到 ADR 接受并有 §13 的证据。 该草案的本次审阅修订已明确编码、拒绝/trap 优先级、输入计数和身份边界，候选向量见 [修订记录](../testing/RIR-ADR-REVISION-20261023.md)；这不构成 RIR 实现或 conformance 通过。

**依赖。** OQ-02、OQ-10、OQ-11、OQ-12。

**2026-11-14 M2 实验证据。** [多来宾容量排序通用契约验收](../testing/MULTIVM-SORT-CONTRACT-20261114.md)。固定容量排序用记录数独立记账。同宿主三来宾验证派发预留、无答复全额计入、一次补算及无在途检查点的协调器交接。OQ-05 继续为 `OPEN`。

**2026-11-15 R2 实验证据。** [双机 nVM 验收](../testing/DUALHOST-MULTIVM-R2-20261115.md)。B 侧断连无发布，丢答复全额入账并在冻结预算内补算。证据范围是固定用例与可信 LAN。OQ-05 继续为 `OPEN`。

## 8. OQ-06 — 验证器、结果等价与验证会话

**问题。** 不同任务类型如何声明可验证性、结果等价关系和验证成本，而不引入全局真相裁决者？

**备选路径。**

1. 验证器注册：协议内置；版本化开放注册表；Requester 携带代码；部署白名单；能力协商。
2. 等价关系：字节相等；规范化后相等；容差区间；领域判定器；属性满足；统计分布一致。
3. 验证方式：重复执行；抽样检查；证明验证；差分检查；外部 oracle；人工审核作为终态外流程。
4. 验证器信任：完全确定性；可复现沙箱；多实现交叉检查；验证器本身也被取样验证。
5. 会话快照：任务创建时冻结；首个样本时冻结；每轮冻结；由部署协调层提供快照。

**当前建议。** 为每个 TaskType 冻结 `VerificationProfile`，至少声明 `VerifiedClaim`、`ExcludedClaims`、输入域、结果等价、确定性、成本、安全/活性参数、失败模式和版本。Profile 分为 `DIRECT_VERIFIED`、`PROOF_VERIFIED`、`REEXEC_BOUNDED` 和 `REEXEC_AUDIT_ONLY`。开放注册只增加候选验证器，不能自动赋予真相权；Profile 是后续验证工作的严格前置对象。

**局部状态（2026-08-21）。** VerificationProfile 的 P0-1A 语义已由 [`../03-protocol/verification-profile-schema.md`](../03-protocol/verification-profile-schema.md) 和 AUD-20260821-10 关闭；P0-1B 已开始但未关闭。OQ-06 仍保持 `OPEN`，因为具体任务族 predicate、完整注册/撤销、ExecutionCapability/会话快照实现和全量 conformance 尚未完成。

**关闭证据。** VerifierProfile 模式、注册与撤销规则、等价关系测试、验证器不一致处理、会话快照和恶意验证器反例。

**依赖。** OQ-02、OQ-07、OQ-11、OQ-13。

## 9. OQ-07 — 有限总体序贯验证与停止定理

**问题。** 当前候选方向能否在有限 Provider/结果总体、不放回抽样和可选停止下，给出与协议终态一致的有效错误控制？

**备选路径。**

1. 统计框架：有限总体 e-process；不放回 confidence sequence；固定样本超几何检验；保守组合界；Bayesian sequential policy 仅作效率层。
2. 估计目标：错误结果比例；正确结果比例；多数类别质量；任务损失函数；最坏可接受风险。
3. 抽样单位：Provider；Receipt；控制簇；分片；验证操作。
4. 随机性：Requester 承诺种子；多方提交—揭示；可验证随机函数；外部随机信标；部署共识随机性。
5. 停止：单一 TRUSTED 边界；可信/不可解双边界；预算耗尽；证据停滞；硬风险上限触发。
6. 多重性：逐任务保证；跨分片校正；跨轮次 alpha spending；统一 anytime-valid 过程。
7. `Nmax`：`min(population, budget, policy)`；其中 policy 可由风险级别、验证成本和硬上限共同决定。

**当前结论。** 单候选、有限总体、不放回的 e-process 数学内核已经条件闭合：错误候选的支持能力集合必须在 draw 前固定、与随机排列独立且大小不超过 \(B\)；混合权重预先冻结；以精确算术实现。递推、闭式、全枚举和 DP oracle 已完成对拍，且“只限制实际支持票数、允许事后选择能力集合”已有精确反例。Bayesian policy 只用于采样/成本效率，不是第二真理闸门。

OQ-07 因而拆成两个状态：条件定理和数值语义为 `DECIDED / DERIVED`；具体部署如何建立 \(B\)、校准 \(Q\)、证明集合冻结/独立性并处理多任务重复风险，仍为 `OPEN/CANDIDATE P0`。未建立这些前提时只能使用 `REEXEC_AUDIT_ONLY`。

**剩余关闭证据。** 可部署的能力集合上界证明；\(Q,\delta_Q\) 的同类锚定校准与外推规则；随机排列和 Snapshot conformance；跨任务错误预算；固定算术编码；第二语言独立实现复核。当前数学说明与测试见 [`../06-research/verification-round-mathematical-model.md`](../06-research/verification-round-mathematical-model.md) 和 [`../../tests/verification_model/README.md`](../../tests/verification_model/README.md)。

**依赖。** OQ-06；与 OQ-08 强耦合。

## 10. OQ-08 — Sybil、相关性、隐私与最坏暴露

**问题。** 在无法证明身份独立、Provider 可能共控或共享故障源时，如何避免伪独立证据造成过度确信？

**备选路径。**

1. 处理单位：把所有未知身份视为一个簇；基于已知关系合并；软相关权重；最坏情况上下界；分层风险模型。
2. 信号：控制声明；资金来源；网络/基础设施；软件镜像；行为相关；外部证明；历史共同故障。
3. 折扣：有效样本量；簇内只计一次；协方差上界；证据权重封顶；贝叶斯层次模型。
4. 暴露控制：单身份上限；单簇上限；单故障域上限；任务级总损失上限；资金级上限；组合上限。
5. Sybil 成本：保证金；资源证明；付款历史；速率限制；邀请/证明；不依赖身份成本，只依赖硬风险上限。
6. 隐私：原始信号公开；仅公开簇标签；零知识关联证明；本地评分；只保留保守上界。

**当前建议。** 不宣称解决 Sybil，也不把经济成本当作独立性证明；优先采用相关性簇/证据折扣，并始终叠加任务、簇和系统级硬暴露上限。`REEXEC_BOUNDED` 还要求这些机制在 draw 前形成“可能支持错误候选”的能力集合上界 \(B\)，不能用实际票数替代。V1 不追求通用自然人唯一性证明；官方主网可在版本化 assurance、工程审计、有效期和绝对损失预算内接受有限相关性风险。未被该 assurance 覆盖的部署必须降级为 `REEXEC_AUDIT_ONLY` 或 `DISABLED`。

**关闭证据。** 协议接口关闭需要簇引用、Snapshot/Capability 绑定、降级和损失上限 Schema；具体主网启用需要威胁覆盖、隐私影响评估、簇错误合并/漏合并敏感性、对抗仿真、参数校准、assurance 发布/撤销和损失预算。通用自然人唯一性证明不在关闭条件内。

**依赖。** OQ-03、OQ-07、OQ-09、OQ-10。

## 11. OQ-09 — 能力估计、冷启动与暴露决策

**问题。** 如何从可归因的 PerformanceEvidence 形成带不确定性的 CapabilityEstimate，并据此限制暴露，而不创造 Rank 或 Reputation 权威？

**备选路径。**

1. 估计：Beta/Dirichlet 后验；置信下界；Glicko 类不确定性；校准分类器；领域分层模型；非参数区间。
2. 任务迁移：完全隔离；任务族共享；层次迁移；基于特征相似度；禁止跨域迁移。
3. 时间：不衰减；固定窗口；指数衰减；变化点检测；环境/版本分段。
4. 冷启动：零暴露；统一小额探索；Requester 自担探索；保证金支持；外部证明提供先验但不提供真相权。
5. 决策：下置信界门槛；风险预算优化；多臂探索；最坏损失约束；多目标效用。
6. 发布：公开全部证据；公开摘要；选择性披露；本地估计；可验证计算证明。

**当前建议。** 保留原始、可追踪的 PerformanceEvidence；估计必须携带不确定性与适用域；ExposureDecision 使用保守下界和硬上限；新 Provider 获得有限、可预算的探索机会，不因身份或能力证据取得验证、治理或最终审计权。

**关闭证据。** 数据生成模型、校准曲线、冷启动公平性和损失上限、漂移测试、操纵实验、跨域迁移反例，以及从证据到暴露的可解释测试向量。

**依赖。** OQ-08、OQ-10、OQ-14 中的任务分类。

## 12. OQ-10 — 资金、故障归因、结算与偿付

**问题。** 不同 FundingPolicy 下，如何在成功、失败、超时、争议、预算耗尽和系统故障时确定付款、退款、补贴与损失承担？

**备选路径。**

1. 资金来源：Requester fee；预置 reserve；外部 subsidy；可选 issuance；混合资金池。
2. 锁定：全额预付；按阶段托管；信用额度；Provider 自担后结；保险/保证金。
3. 计价：固定价；竞价；资源量；有效 Receipt；风险调整价格；结果价值分享。
4. 故障归因：严格可证明过错；按状态机械分配；共享损失；保险池；人工争议作为协议外流程。
5. 退款：全退；按已验证工作扣除；分级退款；不退但转为重试预算。
6. 处罚：仅拒付；罚没保证金；降低未来暴露；速率限制；不采用惩罚，仅硬上限。
7. 偿付不足：按比例；优先级队列；停止新任务；外部补资；显式 `FUNDING_EXHAUSTED`。
8. 结算载体：内部账本；外部支付；链上合约；离线票据；多适配器统一语义。

**当前建议。** Task 创建时冻结 FundingPolicy 和最大负债；所有状态都映射到确定的资金结果；资金不足必须形成显式终态，不能隐性透支；结算绑定不可重放的权利 ID 并满足 at-most-once。发行只是可选政策，不是协议默认或安全假设。

**关闭证据。** 完整状态×故障方×资金来源结算矩阵、守恒性质、最大负债证明、重复执行测试、适配器幂等测试、破产与舍入案例。

**依赖。** OQ-02、OQ-04、OQ-05、OQ-08、OQ-11。

## 13. OQ-11 — 一致性、时钟、分区与适配器语义

**问题。** 协议如何在异步网络、重复消息、时钟漂移、协调层分区和不同适配器下保持合法状态与一致经济效果？

**备选路径。**

1. 状态协调：单一事务数据库；复制状态机；事件溯源；CRDT/合并状态；外部账本。
2. 排序：逻辑序号；Lamport/混合逻辑时钟；协调层高度；显式因果引用；全序日志。
3. 终局：立即数据库提交；确认深度；法定人数证书；可逆窗口；经济终局与数据终局分离。
4. 分区策略：可用性优先并封顶暴露；一致性优先暂停；按操作分类；只读降级。
5. 适配器：统一事务接口；outbox/inbox；补偿事务；幂等调用；两阶段提交；可验证收据。
6. 区块链：不用；仅结算适配器；仅审计锚定；作为某部署的协调层；绝不作为协议必需条件。

**当前建议。** 规范定义事件的因果前置条件、幂等键和可接受终局，不强制单一协调技术；分区期间不得超过预声明风险上限；适配器失败必须可重试或进入明确终态。官方主网必须选择一个版本化 append-only/finality contract 并绑定 checkpoint/inclusion/consistency verifier；区块链、Merkle transparency log 或等价模块都可以实现，不能因“上链”跳过 contract 测试。

**关闭证据。** 状态转移模型、分区与重放测试、时钟无关性分析、终局定义、适配器契约、故障矩阵和至少两个异构适配器的一致结算结果。

**依赖。** OQ-02、OQ-05、OQ-10。

## 14. OQ-12 — 审计日志、保留、可观测性与恢复

**问题。** 需要保留哪些事件和证据，才能在不依赖运行时裁决者的情况下重建决策、诊断失败并恢复服务？

**备选路径。**

1. 日志：完整事件溯源；规范事件加派生状态；最小 Receipt；部署自定义日志。
2. 完整性：哈希链；Merkle 承诺；签名事件；WORM 存储；外部时间戳/锚定。
3. 保留：永久；按任务风险分层；法律/合同周期；只保留承诺，原文到期删除。
4. 隐私：明文审计；字段加密；分离身份与任务数据；选择性披露；聚合指标。
5. 监控：协议终态指标；风险预算；资金守恒；验证误差；Provider/簇集中度；适配器健康。
6. 恢复：快照加日志；多区域复制；冷备；从 Receipt 重放；外部协调层恢复。

**当前建议。** 规定最小规范事件和可验证 Receipt，允许部署增加日志；官方主网状态转换只有在被 assurance 允许的日志后端 finalized 后生效，消费方验证 inclusion/consistency。保留策略按数据敏感性和争议窗口分层；所有派生决定必须能追溯到冻结输入与规则版本；恢复测试必须覆盖资金和终态不重复。日志忠实性属于工程 contract、权限和恢复审计，不再被错误要求由 Schema 证明现实。

**关闭证据。** 事件模式、追踪 ID、保留矩阵、隐私评审、RPO/RTO 目标、重放与灾备演练、关键指标和告警阈值。

**依赖。** OQ-02、OQ-05、OQ-10、OQ-13。

## 15. OQ-13 — Maintenance、发布、撤销与管理成本

**问题。** 如何提供版本发布、漏洞响应和兼容性维护，而不让 Maintenance 演变为运行时裁决、真相或资源分配权威？

**备选路径。**

1. 维护形式：单维护者；多维护者；基金会；公司托管；多实现工作组；无正式组织。
2. 发布授权：签名标签；阈值发布；可复现构建；透明日志；实现自行选择版本。
3. 规范变更：粗略共识；正式投票；ADR + 兼容性审查；多版本并存；不可变规范新版本分叉。
4. 撤销：安全公告；撤销列表；强制停机开关；部署自行决策；协议级版本失效日期。
5. 紧急响应：单人响应；轮值小组；阈值授权；仅发布建议不触碰运行时；预先定义的兼容降级。
6. 管理资金：志愿维护；赞助；基金；服务收入；协议费用；不设置持续组织。

**当前建议。** v0.5 采用最小维护边界：维护者管理规范版本、参考工件、安全披露和官方主网 `MainnetAssuranceProfile`，但不能替任务裁决、改写证据、改变权重或分配运行时收益。assurance 只能限网络、先承诺、版本化并在运行中保守减权；主网外不继承。先用签名发布、透明日志、可复现构建、ADR 和公开兼容性记录；只有在明确净收益和最小权限后才继续扩张组织。

**关闭证据。** 维护者权限表、发布/撤销流程、安全政策、密钥轮换、冲突与离任方案、成本预算、组织扩张/收缩触发器和法律载体判断。

**依赖。** OQ-01、OQ-06、OQ-12。

## 16. OQ-14 — 异构任务与未来安全增强

**问题。** 在不扩大 v0.5 核心的前提下，未来如何支持非确定性、隐私敏感、数据本地或高价值任务？

**备选路径。**

1. 非确定性结果：容差谓词；统计验收；属性测试；多次运行分布；人工外部审核。
2. 隐私计算：数据本地执行；可信执行环境；多方计算；同态加密；零知识证明；只暴露摘要。
3. 高价值任务：更高冗余；独立故障域；外部审计；保险/保证金；更严格硬暴露上限。
4. 数据与硬件约束：能力声明；远程证明；第三方认证；部署白名单；Requester 风险接受。
5. 验证增强：可验证计算；SNARK/STARK；交互式证明；领域证明系统；抽样与证明混合。
6. 试点路线：纯确定性 CPU 任务；可重复容器任务；数据本地任务；非确定性/ML 任务；高价值生产任务。

**当前建议。** V1 Profile 已分别登记 CORE、DEFERRED 和 REJECTED。V1 先以通过 Rust Profile 降级到规范 RIR、由 RPR 执行、Logical Object 输入、effects 封闭、资源有界且结果精确可比的 CPU 任务作为验证对象。unsafe Rust、完整 `std`/宿主 OS effects、原生执行、GPU/专用加速器、共享可变内存、容差结果和非确定性任务延期；未来只能通过独立 Profile、conformance、威胁更新和 ADR 引入。TaskType/VerifierProfile 负责扩展验证语义，核心不预设 TEE、链或零知识系统。

**关闭证据。** 至少一个受控试点、任务类型安全剖面、成本—风险对比、失败模式、可移植性测试和是否需要新 ADR 的判断。

**依赖。** 核心 G1/G2 稳定后再推进。

## 18. 已关闭的旧方向

以下方向不再作为 v0.5 开放问题。重新开启必须提供新证据，并通过 ADR 说明为何原决定失效。

| 旧方向 | 状态 | v0.5 结论 |
|---|---|---|
| 把 Rank/Reputation 作为全局实体或权威 | REJECTED | 使用 PerformanceEvidence → CapabilityEstimate ± Uncertainty → ExposureDecision |
| 固定角色垄断规划、验证或结算 | REJECTED | 这些是 permissionless functions；安全来自有效性规则和可验证承诺 |
| 默认以 51% 或简单多数决定正确性 | REJECTED | `Nmax = min(population, budget, policy)`；接受条件取决于声明模型和风险目标 |
| 默认通过发行支付 Provider | REJECTED | 发行只是 FundingPolicy 的可选来源 |
| Foundation/委员会成为运行时 Principal 或个案最终裁判 | REJECTED | Maintenance 可以发布主网 assurance，但不能改个案、权重或终态 |
| 把区块链作为协议、安全或真相前提 | REJECTED | 区块链最多是可选协调、审计或结算适配器 |
| 把 TRUSTED 解释为绝对正确 | REJECTED | TRUSTED 只表示在冻结模型、证据与阈值下满足接受条件 |
| 把身份数量视为独立证据数量 | REJECTED | 不假设身份独立；需要相关性处理与硬暴露上限 |
| 单值 verdict 与 flag set 必须二选一 | SUPERSEDED | 保存完整 `CauseSet`，由冻结 reducer 派生唯一 `EffectiveVerdict` |
| 增加检查必须增加第三个 Dispatch scope 权威 | REJECTED | active Lease 是唯一执行权威；Dispatch/RPR 多点校验派生 capability |
| 所有来源忠实性都必须先有形式证明 | REJECTED | Schema/算法需确定；日志、权限、恢复和部署事实采用限域工程证据与 fail-closed |

## 19. 问题关闭流程

关闭任一问题时必须完成：

1. 将实验、证明、工程审计、故障注入、外部意见或测试链接到“关闭证据”，并标明它支持结构、算法、来源还是部署哪一层；
2. 明确选择了哪个备选路径，拒绝了哪些路径及原因；
3. 更新相应规范、架构、威胁、不变量和分析文档；
4. 如果改变不可约实体、信任边界、资金权利或兼容性，新增 ADR；
5. 更新 `current-status.md` 的事实表、Gate 和日志；
6. 将状态改为 `DECIDED`；只有实现/证明验证完成后再改为 `CLOSED`。

如果证据推翻当前建议，应直接记录证伪，不得为了维持路线而弱化关闭标准。
